# Implementation Plan: Exercise Catalog

Module id: `exercise-catalog`

Status: Approved
Approved: 2026-09-21

Specification: `SPEC-exercise-catalog.md`

## Overview

Build the exercise catalog as the second local-first module. The implementation adds a versioned built-in manifest, SQLite-backed custom exercises and built-in visibility overrides, one reactive consumer contract, a dedicated catalog route, and a reusable inline picker for later routine programming. The catalog remains independent of routine prescriptions, gym equipment, workout logging, and history.

## Current State

- Expo SDK 57, React Native 0.86, React 19.2, Expo Router, Expo SQLite, Zod, i18next, Jest, and React Native Testing Library are already configured.
- `src/db/migrate.ts` owns ordered migrations through `PRAGMA user_version`; schema version 1 contains only `training_preferences` and runs in an exclusive transaction.
- `AppProviders` already provides SQLite, i18next, and the global training-preferences provider.
- English and Spanish resources use one typed resource shape with English fallback.
- The project has generated Gluestack primitives for buttons, radio controls, typography, layout, and loading, but no generated text input.
- The protected app currently has a landing route and one training-preference settings route.

## Architecture Decisions

### 1. Stable opaque identities

All exercise IDs are branded strings containing exactly 32 lowercase hexadecimal characters. Built-in IDs are checked-in random 128-bit literals. Custom IDs are generated by SQLite with `lower(hex(randomblob(16)))`. Both origins therefore use the same opaque shape, and no consumer can infer origin, name, group, or order from an ID.

IDs never change during rename, regroup, availability changes, translation changes, or manifest migrations. A released built-in ID is never reused for another exercise.

### 2. Schema version 2

Migration 2 is additive and runs after the existing training-preferences migration in the same ordered migration system. It creates exactly these tables:

```sql
CREATE TABLE custom_exercises (
  exercise_id TEXT PRIMARY KEY NOT NULL
    CHECK (
      length(exercise_id) = 32
      AND exercise_id NOT GLOB '*[^0-9a-f]*'
    ),
  display_name TEXT NOT NULL
    CHECK (length(display_name) BETWEEN 1 AND 80),
  name_key TEXT NOT NULL UNIQUE
    CHECK (length(name_key) > 0),
  muscle_group TEXT NOT NULL
    CHECK (
      muscle_group IN (
        'chest',
        'upper-back',
        'lats',
        'shoulders',
        'biceps',
        'triceps',
        'forearms',
        'quads',
        'hamstrings',
        'glutes',
        'calves',
        'adductors',
        'core',
        'lower-back'
      )
    ),
  is_available INTEGER NOT NULL DEFAULT 1
    CHECK (is_available IN (0, 1))
);

CREATE TABLE hidden_builtin_exercises (
  exercise_id TEXT PRIMARY KEY NOT NULL
    CHECK (
      length(exercise_id) = 32
      AND exercise_id NOT GLOB '*[^0-9a-f]*'
    )
);
```

No built-in name or translation is copied into SQLite. Absence from `hidden_builtin_exercises` means the built-in is available. Hiding uses `INSERT OR IGNORE`; restoring uses `DELETE`, making both operations idempotent. Custom archive/restore updates `is_available` in place.

The existing forward-only migration runner remains authoritative. `user_version` advances to 2 only after both tables are created successfully; transaction failure rolls back the tables and version together. No destructive down migration is added to an installed mobile database.

### 3. Deterministic name validation

Custom-name validation is pure and shared by forms and repository boundaries:

- Apply JavaScript Unicode `trim()` and preserve that trimmed value for display.
- Reject an empty value, more than 80 Unicode code points, and control/format characters.
- Build `name_key` from the trimmed value with NFC normalization and locale-independent lowercase behavior using the fixed `en-US` locale.
- Compare only custom `name_key` values, including archived rows. Accents remain significant for uniqueness because the specification requires case-insensitive, not accent-insensitive, duplicate detection.
- Permit a custom name to equal any localized built-in name.

The database unique constraint is a final integrity guard. Public operations validate against the loaded catalog before writing; because provider mutations are serialized, a uniqueness constraint failure not caused by user-visible duplication is treated as `persistence-error` rather than guessed from error text.

### 4. Versioned built-in manifest

The manifest is a readonly array in fixed muscle-group order. Every entry stores only an opaque ID, a muscle-group ID, and a translation key. English and Spanish resources contain the 74 names specified in the approved spec and the 14 muscle-group labels.

Manifest validation proves unique valid IDs, exact exercise membership and grouping, complete translation keys in both languages, and deterministic source order. Future additions, removals, renames, or regrouping require a new reviewed catalog data migration that preserves every released ID and resolvable historical reference.

### 5. Pure catalog model

React-free model modules own:

- Branded IDs, muscle-group values, fixed group order, exercise and mutation result types.
- Custom-name parsing and duplicate keys.
- Built-in and persisted-row validation.
- Accent-insensitive search using NFD normalization, combining-mark removal, and lowercase comparison.
- Availability filtering and grouping.
- Locale-aware name sorting with deterministic tie breakers: locale display name, exact display name, origin, then opaque ID.

The provider supplies the current i18n language to sorting. Custom names are never translated.

### 6. Narrow persistence boundary

`ExerciseCatalogRepository` reads all custom rows and hidden built-in IDs, validating the complete result with Zod before returning anything. One invalid row rejects the load with a recoverable validation error; it is never silently omitted or repaired.

Repository writes use bound parameters. Custom creation runs ID generation, insertion, and ID read-back in one exclusive transaction so any failure rolls back the whole mutation. Update/archive operations check affected-row counts. Built-in visibility writes validate IDs against the manifest before reaching persistence.

### 7. One reactive consumer contract

`ExerciseCatalogProvider` combines the manifest, current translations, and persisted state and exposes one `useExerciseCatalog()` interface:

```ts
type CatalogMutationResult<T> =
  | { ok: true; value: T }
  | { ok: false; reason: CatalogMutationFailure };

type ExerciseCatalogContextValue = {
  state: ExerciseCatalogState;
  listAvailable: (
    query?: string,
    muscleGroup?: MuscleGroup | null,
  ) => readonly CatalogExercise[];
  listUnavailable: (
    query?: string,
    muscleGroup?: MuscleGroup | null,
  ) => readonly CatalogExercise[];
  resolve: (id: ExerciseId) => CatalogExercise | null;
  createCustom: (input: CustomExerciseInput) => Promise<CatalogMutationResult<ExerciseId>>;
  updateCustom: (
    id: ExerciseId,
    input: CustomExerciseInput,
  ) => Promise<CatalogMutationResult<CatalogExercise>>;
  setAvailability: (
    id: ExerciseId,
    isAvailable: boolean,
  ) => Promise<CatalogMutationResult<CatalogExercise>>;
  retryLoad: () => void;
};
```

State distinguishes `loading`, `ready`, `load-error`, `mutating`, and `mutation-error`, while retaining the last successfully loaded or mutated durable exercise array. Mutations are serialized and pessimistic: the shared array changes only after the SQLite write succeeds. Failures return the required machine-readable reason and retain prior state. Locale changes re-resolve built-in names and re-sort mounted consumers without persistence writes or restart.

### 8. Dedicated catalog experience

Add the thin route `src/app/(app)/exercises/index.tsx` and link it from the protected app landing screen. The feature screen uses a `SectionList` grouped by the fixed muscle-group order, a generated Gluestack input for search, one horizontally scrollable group filter, and an explicit available/unavailable view toggle.

Custom create/edit forms expand in the catalog flow rather than opening a modal. This avoids unnecessary overlay complexity while retaining logical focus: cancellation returns focus to the invoking control, successful edits retain focus on the edited row, and actions that remove a row from the current view move focus to the view toggle and announce the result. Built-in rows expose hide/restore only; custom rows expose edit and archive/restore.

### 9. Reusable inline picker

`ExercisePicker` is route-independent and receives `selectedId` and `onSelect(id)`. It uses the same available selector, search, muscle filter, and custom form. Hidden and archived entries never appear. A successful inline creation invokes `onSelect` with the newly durable ID; cancellation and save failure retain the prior selection and focus.

The picker is delivered and component-tested now but is not mounted into a routine route until the `routine-programming` module consumes it.

### 10. Generated UI components and dependencies

Use the checked-in Gluestack generator configuration to add the input primitive under `src/components/ui/input/`. The generator must not add a runtime dependency or change package versions. If it proposes a dependency change, stop and ask before proceeding. Existing generated buttons, radio controls, layout, and text components remain the first choice for interactive UI.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Released built-in IDs drift during manifest edits | High | Use checked-in opaque literals, exact-manifest tests, and treat later changes as reviewed data migrations. |
| SQLite and active React state diverge after failure | High | Serialize mutations, write pessimistically, use an exclusive create transaction, and update active state only after durable success. |
| Unicode matching differs across devices/locales | Medium | Use explicit normalization pipelines and a fixed locale for duplicate keys; test accents, composed/decomposed text, case, and unsupported app locales. |
| An invalid persisted row is partially exposed | High | Parse the complete repository result before combining it with the manifest; reject the load as one recoverable error. |
| Catalog rows become slow or unstable as the manifest grows | Medium | Keep normalization pure, use one `SectionList`, stable opaque keys, deterministic sorting, and no per-row database reads. |
| Generated UI code adds an unauthorized dependency | Medium | Inspect generator output and package diffs immediately; stop for approval before accepting dependency changes. |
| Focus is lost when a mutation removes the active row | Medium | Define explicit fallback refs and announcements, then manually verify VoiceOver and TalkBack on both availability views. |
| Future modules bypass the catalog boundary | Medium | Export the hook/types from feature-owned modules only and contract-test resolution of unavailable IDs. |
